# v3 training-data configurations

This folder holds the NeMo `input_cfg` YAMLs that drive the audio-adapter
training mix for the **v3** dataset generation. Two training options are
provided: a single one-step mix, and a 3-stage curriculum.

## Files

| File | Purpose |
|---|---|
| `input_cfg_train.yaml`          | **Single-step** training (adapter + LoRA on the LLM trained together). |
| `input_cfg_train_stage1.yaml`   | **Stage 1 of 3** — alignment (train adapter only; encoder + LLM frozen). |
| `input_cfg_train_stage2.yaml`   | **Stage 2 of 3** — encoder tuning (train adapter + encoder; LLM frozen). |
| `input_cfg_train_stage3.yaml`   | **Stage 3 of 3** — full fine-tune (train adapter + encoder + LoRA on LLM). |
| `input_cfg_train_weighted.yaml` | Fully-weighted form of `input_cfg_train.yaml` (every leaf carries its computed share), regenerated by the suggestion pipeline below. |
| `metadata.csv`                  | Per-manifest metadata (samples, duration, language, task, sub-task, etc.) extracted from the JSONL manifests by `assets/generate_csv_metadata.py`. |

## Task budget — head-to-head

| Task | One-step | Stage 1 (adapter) | Stage 2 (+enc) | Stage 3 (+LLM LoRA) |
|---|---:|---:|---:|---:|
| **ASR**               | **34 %** | **50 %** | 30 %     | 25 %     |
| **AST**               | 11 %     | 20 %     | 13 %     | 12 %     |
| **QA**                | **34 %** | 16 %     | **36 %** | **40 %** |
| **AQA** (sound+music) | 10 %     | 8 %      | 12 %     | 12 %     |
| **OTHER**             | 10 %     | 5 %      | 8 %      | 10 %     |
| **task_switching**    | **1 %**  | **1 %**  | **1 %**  | **1 %**  |
| **Sum**               | 100 %    | 100 %    | 100 %    | 100 %    |

Across the curriculum the two key trajectories are:

- **ASR**: 50 % → 30 % → 25 %  *(decreases as encoder/LLM unfreeze and reasoning takes over)*
- **QA**: 16 % → 36 % → 40 %  *(ramps up — main reasoning push happens once the LLM is trainable)*

`task_switching` is held at exactly 1 % in every configuration to keep multi-turn
exposure constant.

## When to use which

### Single-step (`input_cfg_train.yaml`)

Use this when you train the adapter and the LLM (with LoRA) in one go, with no
intermediate checkpoints. The mix is balanced (ASR 34 % / QA 34 %) so the model
gets both a strong recognition foundation and substantial reasoning supervision
from the start.

### 3-stage curriculum (`input_cfg_train_stage{1,2,3}.yaml`)

Use this if you want to follow a curriculum that mirrors what works for
state-of-the-art audio-language models. The three stages progressively unfreeze
parameters and shift the data mix:

| | Trainable parameters | Why this data mix |
|---|---|---|
| **Stage 1** | adapter only | The adapter alone has to learn to project audio embeddings into the LLM token space. Recognition tasks (ASR + AST) give the cleanest, most directly-supervised signal for this — hence ASR 50 %, AST 20 %. QA and other tasks are kept small (they're a poor learning signal when the adapter is still random). |
| **Stage 2** | adapter + encoder | The encoder now adapts to a wider task distribution while the LLM stays frozen. ASR drops to a stable floor (30 %) and QA jumps to 36 % — the main reasoning push happens here. |
| **Stage 3** | adapter + encoder + LoRA on LLM | The LLM is unfrozen (via LoRA) to learn reasoning and skill acquisition on top of an already-aligned encoder + adapter. QA peaks at 40 %, ASR holds at its floor of 25 %, and OTHER expands for multitask polish. |

## How the weights were computed

For every file, the top-level percentages above are **explicit weights** on the
six top-level `task: {asr, ast, qa, aqa, other, task_switching}` groups. The
within-task structure (per-language splits, sub-task sub-groups, YouTubeFr
collection wrap, etc.) is **identical across all four files** — only the six
top-level weights differ.

## Within-task structure (unchanged across files)

- **ASR** — fr 30 %, en 30 %, de 8 %, es 8 %, it 6 %, nl 5 %, pt 5 %, ar 8 %.
  YouTubeFr's 7 splits are wrapped under a sub-group with `weight: 0.18` so the
  collection competes as one entity (not seven).
- **QA** — en 44 %, fr 44 %, de 4 %, es 4 %, it 4 %. Vigogne–Alpaca has an
  explicit `weight: 0.03` to cap its share at ~3 % of FR QA.
- **AST** — flat list of 31 language pairs, data-driven within the group.
- **AQA** — sound 50 % / music 50 %, each broken down by language and dataset.
- **OTHER** — organised by sub-task: `gender_reco`, `age_reco`, `temporal`,
  `diarization`, `voice_captioning`, `language_reco`, `emotion_reco`, plus a
  small sentence-stress bucket. `gender_reco` and `age_reco` use 35 / 35 / 10 /
  10 / 10 splits for en/fr/de/es/it (with `age_reco` letting de/es/it share the
  remaining 30 % data-driven so es isn't over-sampled). `diarization` uses the
  natural en/fr sample ratio (22 / 78).
- **task_switching** — single `MiscMultiTurn` manifest.

Changing within-task structure in one file means manually replicating it in
the other three; the four files are intentionally kept structurally identical
so only the six top-level weights need attention.

## Regenerating `input_cfg_train_weighted.yaml` and the analysis assets

`input_cfg_train_weighted.yaml` is **not hand-written** — it's produced by the
analysis pipeline in `assets/`. Three steps, from this directory:

```bash
SRC_DIR=../../../../../assets/

# Step 1 — parse the input YAML and every JSONL manifest it references into a
# single metadata CSV (samples / duration / sub-task / language / dataset name).
# This is the slow step (reads every manifest); the workers flag parallelises it.
python $SRC_DIR/generate_csv_metadata.py input_cfg_train.yaml \
    --data_root /data-server/datasets/audio --output_dir . --workers 24

# Step 2 — given the metadata CSV and the original (hand-written) YAML, walk
# the tree and emit a fully-weighted YAML where every leaf has an explicit
# `weight:` field reflecting the resolved data-driven share. The summary table
# printed on stdout is also saved to disk.
python $SRC_DIR/suggest_yaml_cfg.py metadata.csv \
    --metric samples --temperature 2 \
    --input_weights input_cfg_train.yaml --max_passes 20 \
    --output input_cfg_train_weighted.yaml | tee input_cfg_train_weighted_notes.txt

# Step 3 — render before/after dataset-composition donut plots (one per metric)
# plus per-task breakdowns into subfolders. Used purely for visual inspection.
python $SRC_DIR/plot_composition.py metadata.csv \
    --yaml input_cfg_train_weighted.yaml --metric samples --output ./
python $SRC_DIR/plot_composition.py metadata.csv \
    --yaml input_cfg_train_weighted.yaml --metric duration --output ./
```

Re-run steps 2 and 3 (cheap, ~seconds) after every edit to `input_cfg_train.yaml`
to refresh the weighted view and the plots. Step 1 only needs to be re-run when
the underlying JSONL manifests change.

To do the same for one of the stage files, point `--input_weights` (step 2) and
`--yaml` (step 3) at `input_cfg_train_stage{1,2,3}.yaml` and change the
`--output` filename accordingly.

The `Tasks:` line printed by `suggest_yaml_cfg.py` shows the effective
per-task budget after the algorithm processes the tree — it should match the
table above.
