# v4 training-data configurations

This folder holds the NeMo `input_cfg` YAMLs that drive the audio-adapter
training mix for the **v4** dataset generation. It is the successor to **v3**:
same structure and weighting philosophy, with **six new datasets** folded in
(see [What's new in v4](#whats-new-in-v4)). Two training options are provided:
a single one-step mix, and a 3-stage curriculum.

## Files

| File | Purpose |
|---|---|
| `input_cfg_train.yaml`          | **Single-step** training (adapter + LoRA on the LLM trained together). |
| `input_cfg_train_stage1.yaml`   | **Stage 1 of 3** — alignment (train adapter only; encoder + LLM frozen). |
| `input_cfg_train_stage2.yaml`   | **Stage 2 of 3** — encoder tuning (train adapter + encoder; LLM frozen). |
| `input_cfg_train_stage3.yaml`   | **Stage 3 of 3** — full fine-tune (train adapter + encoder + LoRA on LLM). |
| `input_cfg_train_weighted.yaml` | Fully-weighted form of `input_cfg_train.yaml` (every leaf carries its computed share), regenerated by the pipeline below. One is produced per hand-written YAML. |
| `input_cfg_train_weighted_randomorder.yaml` | Same weights as `input_cfg_train_weighted.yaml`, pointing at the shuffled (`_randomorder`) manifests. One per hand-written YAML. |
| `metadata.csv`                  | Per-manifest metadata (samples, duration, language, task, sub-task, etc.) extracted from the JSONL manifests by `assets/generate_csv_metadata.py`. Seeded from v3; the six v4 manifests are appended in place. |
| `make_weighted_configs.sh`      | One-shot script that regenerates `metadata.csv`, all `*_weighted*.yaml`, and the composition plots (see [Regenerating](#regenerating-the-weighted-yamls-and-analysis-assets)). |

## What's new in v4

v4 adds two buckets on top of the v3 mix.

**1. Four audio multi-turn / task-switching sets** (fold into the
`task_switching` bucket, raised from 1 % to 2 %):

| dataset | records | content | tag |
|---|---:|---|---|
| `misc/multilang/context/CVMultiTurn/mixed`            | 1,000,000 | CommonVoice, 8 langs, transcription + fr↔* translation | `multiturn_asr_ast` (mixed) |
| `misc/fr/context/MLSMultiTurn/mixed`                  | 73,308    | MLS-French temporal windows + chapter navigation | `multiturn_temporal` (fr) |
| `misc/en/context/SLUEMultiTurn/mixed`                 | 13,325    | SLUE-SQA5 localisation + linked chains + spoken question | `multiturn_temporal` (en) |
| `sounds/audio-question-answering/en/context/clotho_aqa_multiturn/mixed` | 1,952 | Clotho-AQA questions about sounds | `multiturn_aqa` (en) |

These are built from annotated corpora and were verified against the source
annotations, so they are the highest-quality new material and safe to use
as-is. Every leaf in the bucket carries an **explicit weight** so the split
across the four multi-turn kinds is balanced *and* the very small sets are not
blown up (see [Within-task structure](#within-task-structure-shared-across-all-four-files)).

**2. Two text-only instruction / chat sets** (new `text_only` bucket, 1 %):

| dataset | records | avg. turns |
|---|---:|---:|
| `text_only/en/nemotron_posttraining_v3_chat_chat`                 | 218,343 | ~6.0 |
| `text_only/en/nemotron_posttraining_v3_chat_instruction_following`| 85,679  | ~4.7 |

These have **no audio turn** — every turn is text. Their job is to preserve the
LLM's text instruction-following and multi-turn chat ability while it is
fine-tuned with LoRA (an anti-forgetting regulariser). They are kept
**deliberately small**: their dialogue structure and constraint compliance are
strong, but the data **fabricates facts fluently and invisibly** with no cheap
filter. So this bucket is a *text-skills regulariser, never a knowledge source*.
Because they only exercise the (frozen) LLM in stages 1–2, they are **disabled
in stages 1 and 2** and enabled only in **stage 3** (LLM trainable),
concentrated at 2 % there.

> The path says `text_only/en/…` but a small fraction of the conversations are
> non-English. This is a minor tail; the bucket is tagged `en`.

The 2 pp for the two new buckets in the one-step config are taken from ASR
(34 % → 32 %). Note that `CVMultiTurn` is itself transcription/translation, so
the *effective* recognition exposure barely drops.

## Task budget — head-to-head

| Task | One-step | Stage 1 (adapter) | Stage 2 (+enc) | Stage 3 (+LLM LoRA) |
|---|---:|---:|---:|---:|
| **ASR**               | 32 %     | **48 %** | 28 %     | 23 %     |
| **AST**               | 11 %     | 20 %     | 13 %     | 12 %     |
| **QA**                | **34 %** | 15 %     | **35 %** | **38 %** |
| **AQA** (sound+music) | 10 %     | 8 %      | 12 %     | 11 %     |
| **OTHER**             | 10 %     | 8 %      | 10 %     | **12 %** |
| **task_switching**    | 2 %      | 1 %      | 2 %      | 2 %      |
| **text_only**         | 1 %      | 0 %      | 0 %      | 2 %      |
| **Sum**               | 100 %    | 100 %    | 100 %    | 100 %    |

The new-bucket trajectories across the curriculum:

- **task_switching**: 1 % → 2 % → 2 %  *(in stage 1 only the recognition-oriented
  multi-turn sets are enabled — reasoning-heavy multi-turn is poor signal for a
  still-random adapter; all four sets from stage 2 on)*
- **text_only**: 0 % → 0 % → 2 %  *(no gradient reaches the frozen LLM in
  stages 1–2; concentrated in stage 3 where it actually protects text skills)*

## When to use which

### Single-step (`input_cfg_train.yaml`)

Train the adapter and the LLM (with LoRA) in one go, no intermediate
checkpoints. Balanced mix (ASR 32 % / QA 34 %): strong recognition foundation
plus substantial reasoning supervision from the start, with a small multi-turn
and text-skills top-up.

### 3-stage curriculum (`input_cfg_train_stage{1,2,3}.yaml`)

Progressively unfreeze parameters and shift the mix:

| | Trainable parameters | Why this data mix |
|---|---|---|
| **Stage 1** | adapter only | The adapter learns to project audio into the LLM token space; recognition (ASR 48 %, AST 20 %) is the cleanest signal. QA/other kept small (poor signal when the adapter is still random). Multi-turn held at 1 % with **only the recognition-oriented sets** (MiscMultiTurn + CVMultiTurn) enabled; text-only disabled (LLM frozen). |
| **Stage 2** | adapter + encoder | The encoder adapts to a wider distribution. ASR drops to a floor (28 %), QA jumps to 35 %. All four multi-turn sets enabled (task_switching → 2 %); text-only still disabled. |
| **Stage 3** | adapter + encoder + LoRA on LLM | The LLM is unfrozen (LoRA) to learn reasoning on top of an aligned encoder+adapter. QA peaks at 38 %, ASR holds at its floor (23 %), OTHER expands to 12 %, task_switching holds at 2 %, and text-only turns on at 2 % to protect text instruction-following against forgetting. |

## Within-OTHER sub-task trajectories

Unchanged from v3. The within-OTHER weights are tuned per stage so each
sub-task peaks where it gets the most learning value:

| sub-task | One-step | Stage 1 | Stage 2 | Stage 3 | peak rationale |
|---|---:|---:|---:|---:|---|
| `gender_reco`      | 18 %  | 10 %      | **20 %** | 10 %     | acoustic-feature classification — best when the **encoder** is unfrozen (Stage 2) |
| `age_reco`         | 18 %  | 10 %      | **20 %** | 10 %     | same as gender_reco |
| `temporal`         | 18 %  | 8 %       | 8 %      | **20 %** | structured / time-grounded outputs — needs the **LLM** to be trainable (Stage 3) |
| `diarization`      | 18 %  | 8 %       | 8 %      | **20 %** | same as temporal (multi-speaker structured outputs) |
| `voice_captioning` | 12 %  | 8 %       | **12 %** | **14 %** | benefits from encoder prosody (S2) and LLM text generation (S3) |
| `emotion_reco`     | 6 %   | 8 %       | **10 %** | **12 %** | same as voice_captioning |
| `language_reco`    | 6 %   | 8 %       | 6 %      | 6 %      | small, constant |
| sentence-stress    | 4 %   | **40 %**  | **16 %** | 8 %      | prosodic recognition — most useful in alignment / encoder phases (S1 + S2) |

> ⚠ **Note on the sentence-stress trajectory.** The stress datasets are very
> small (~12 K combined), so even with high input weights, `max_passes=20`
> clips their realised share to ~0.6 % in every stage. The "peak at S1 + S2"
> pattern is preserved in the *input* weights but is visually flat in the
> per-leaf probabilities.

## Within-task structure (shared across all four files)

Identical across the four YAMLs — only the top-level task weights, the
within-OTHER weights, and the per-stage enabling of the new buckets differ.

- **ASR** — one-step: fr 29 %, en 29 %, de 8 %, es 8 %, it 6 %, nl 5 %, pt 5 %,
  ar 10 %. In the curriculum the AR share follows **0 % → 20 % → 10 %** across
  phases (phase 1 has AR ASR commented out). YouTubeFr's 7 splits are wrapped
  under a sub-group with `weight: 0.18`.
- **QA** — en 44 %, fr 44 %, de 4 %, es 4 %, it 4 %. Vigogne–Alpaca capped with
  `weight: 0.03`.
- **AST** — flat list of language pairs, data-driven within the group; the four
  AR-involving pairs follow the same **0 % → 20 % → 10 %** trajectory as ASR AR.
- **AQA** — sound 50 % / music 50 %, each broken down by language and dataset.
- **OTHER** — organised by sub-task (see previous section).
- **task_switching** *(v4)* — `MiscMultiTurn` (existing) plus the four new
  multi-turn sets. Every leaf carries an **explicit weight**, chosen so the
  split across the four multi-turn *kinds* is balanced and the tiny sets are not
  blown up. In `hard` mode the explicit weights set the **language-level** share
  within the bucket; the dataset split *within* a language stays data-driven, so
  same-language sets (`Misc`/`CV` in `mixed`, `SLUE`/`clotho` in `en`) divide by
  size. The weights below give these realised shares (verified from the
  `--metric samples` run):

  | leaf | kind (lang) | weight | ≈ share of mix | up-sampling |
  |---|---|---:|---:|---:|
  | `CVMultiTurn`          | `multiturn_asr_ast` (mixed)  | 0.46 | 0.99 % | 0.5× (down) |
  | `MiscMultiTurn`        | `multiturn_mixed` (mixed)    | 0.19 | 0.31 % | 1.5× |
  | `MLSMultiTurn`         | `multiturn_temporal` (fr)    | 0.28 | 0.56 % | 3.8× |
  | `SLUEMultiTurn`        | `multiturn_temporal` (en)    | 0.05 | 0.10 % | 3.8× |
  | `clotho_aqa_multiturn` | `multiturn_aqa` (en)         | 0.02 | 0.04 % | 9.8× |

  The largest up-sampling factor is **9.8×** (vs ~170× if the 2 % bucket were
  filled purely data-driven). `clotho` (1,952 samples) is genuinely tiny, so its
  share is small by design — the `en` language weight is kept low precisely so
  neither `SLUE` nor `clotho` is over-sampled. In stage 1 only `MiscMultiTurn` +
  `CVMultiTurn` are active (weights re-normalised over those two); shares scale
  with the per-stage bucket size (1 / 2 / 2 %).
- **text_only** *(v4)* — `nemotron_*_chat` and `nemotron_*_instruction_following`,
  split data-driven by sample count (~72 % / 28 %). Active in the one-step and
  stage-3 configs only.

Changing within-task structure in one file means manually replicating it in the
other three; the four files are kept structurally identical so that only the
top-level task weights, within-OTHER weights, and new-bucket enabling vary.

## Regenerating the `*_weighted*` YAMLs and analysis assets

The `*_weighted*.yaml` files are **not hand-written** — they are produced by the
analysis pipeline in `assets/`. Run the bundled script from this directory:

```bash
./make_weighted_configs.sh
```

It performs three steps (equivalent to the commands below, with
`SRC_DIR=../../../../assets`):

```bash
# Step 1 — parse the input YAML and every JSONL manifest into metadata.csv
# (samples / duration / sub-task / language / dataset). Slow: reads every
# manifest. metadata.csv is seeded from v3, so only the six v4 manifests are
# parsed; existing rows are reused and task_type/sub_task are refreshed from
# the YAML. Delete metadata.csv (or pass --force_overwrite) to recompute all.
python $SRC_DIR/generate_csv_metadata.py input_cfg_train.yaml \
    --data_root /data-server/datasets/audio --output_dir . --workers 24

# Step 2 — walk the tree and emit a fully-weighted YAML with an explicit
# weight on every leaf; done for each of the four hand-written configs, plus a
# _randomorder twin pointing at the shuffled manifests.
for NAME in input_cfg_train input_cfg_train_stage1 input_cfg_train_stage2 input_cfg_train_stage3; do
    python $SRC_DIR/suggest_yaml_cfg.py metadata.csv --metric samples --temperature 2 \
        --input_weights $NAME.yaml --max_passes 20 --output ${NAME}_weighted.yaml \
        | tee ${NAME}_weighted_notes.txt
    sed 's/.jsonl/_randomorder.jsonl/g' ${NAME}_weighted.yaml > ${NAME}_weighted_randomorder.yaml
done

# Step 3 — before/after composition donut plots (one per metric) + per-task
# breakdowns, for visual inspection.
python $SRC_DIR/plot_composition.py metadata.csv --yaml input_cfg_train_weighted.yaml --metric samples --output ./
python $SRC_DIR/plot_composition.py metadata.csv --yaml input_cfg_train_weighted.yaml --metric duration --output ./
```

Re-run steps 2 and 3 (cheap, ~seconds) after every edit to a hand-written YAML.
Step 1 only needs re-running when the underlying JSONL manifests change.

The `Tasks:` line printed by `suggest_yaml_cfg.py` shows the effective per-task
budget after the algorithm processes the tree — it should match the top-level
table above.
